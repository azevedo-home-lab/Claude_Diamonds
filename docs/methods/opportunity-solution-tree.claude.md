# Operating instructions — Opportunity Solution Tree (Torres)

Binding for the front diamond's Framing zone. Upload this file to the
project knowledge; the human doc (opportunity-solution-tree.md) is
optional background.

## The model, minimum

One tree per product: Outcome (one, measurable customer behavior or
sentiment) → Opportunities (customer needs/pains/desires, from customer
evidence) → Solutions (~3 compared per target) → Assumption tests (test
the riskiest cheaply). Loop: target → candidates → assumptions → test →
discard / refine / retarget.

## Rules

- Framing = producing or extending the OST, never writing a solution
  pitch. The framing artifact names: outcome, opportunity + evidence,
  siblings considered, then candidate solutions.
- Opportunity vs solution test: more than one way to address it? If only
  one, it is a solution in an opportunity's clothes.
- Every opportunity carries an evidence tag: interview-sourced,
  proxy-sourced (tickets, analytics, Pedro's domain experience — legal
  but named), or assumed. An assumed node cannot be target; it becomes an
  open-questions.md entry instead.
- Pedro arrives with a solution → reverse it: which opportunity, for
  whom, what else would address it? Put ≥2 alternatives beside it before
  any prioritization. Single-solution framings stay PROPOSED, flagged
  un-compared.
- Never select a target opportunity by solution effort. Selection uses:
  sizing, market factors, company fit, customer factors. Effort enters at
  the solutions level only.
- Assumption tests are desk-scale evidence (throwaway prototype, data
  pull, interview question) — never a spec; the gate is unchanged.
- Record target-opportunity choices in the decision log with the four
  selection factors stated.
